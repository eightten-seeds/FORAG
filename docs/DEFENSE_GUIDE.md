本指南面向毕业设计答辩、技术面试与项目复盘，包含 5/10 分钟答辩逐字稿、系统演示流、核心负责模块深度解析、30+ 道高频追问题库及简历表述方案。

## 一、5 分钟答辩逐字稿

**【开场与背景】（0:00 - 1:00）**
> 各位老师好！我汇报的项目是《基于 LangGraph 与混合检索的户外功能服装智能养护问答系统》（FORAG）。
> 冲锋衣、GORE-TEX 防水膜和高端羽绒服等户外装备养护要求极其严苛，如水温过高、用错洗剂或烘干不当，会导致昂贵面料不可逆损坏。但目前官方养护手册分散，网上偏方频出；而通用大模型直接回答易产生参数幻觉，且无法提供可靠的证据出处。
> 为此，我们构建了一个「**可检索、可判断、可追溯、可评估**」的证据驱动 RAG 问答闭环。

**【系统架构与本人负责】（1:00 - 2:30）**
> 系统整体分为五个部分：数据与知识库构建、混合检索与证据重排、证据驱动问答闭环、评测与实验验证，以及 Web 交互工程。
> **在项目中，我主要负责核心的 RAG 混合检索与证据重排模块。**
> 针对用户口语表达与官方专业术语脱节的痛点，我们设计了四阶段检索流水线：
> 1. **知识库构建**：从 Arc'teryx、GORE-TEX 等 14 个官方权威来源采集并结构化切分为 234 个规范知识切片，利用 E5-small 模型在 Elasticsearch 9.5.1 中建立文本倒排与 384 维向量混合索引。
> 2. **双路并行召回**：BM25 召回 Top-20，Dense 向量召回 Top-20。
> 3. **RRF 融合**：采用倒数排名融合算法（$k=60$）消除分数量纲差异，合成 Top-30 候选池。
> 4. **Cross-Encoder 重排**：使用多语言交叉编码器对候选切片进行深度语义打分，精选最终 Top-5 证据。

**【闭环协同与实验结果】（2:30 - 4:00）**
> 检索到的证据送入 LangGraph 状态机，由 Evidence Judge 判定证据是否充分。若充分则进入生成并严格标注 `[E#]` 行内出处；若不充分则根据情况触发增量改写检索，或安全转入「需要补充信息」或「证据不足拒绝」状态，坚决不凭空编造。
> 在评测上：
> - 在 16 条冻结正式 TEST 样本与 RAGChecker 事实级自动化评测中，系统的 **Recall@5 达到 87.5%**（14/16 样本命中），事实覆盖率 **Claim Recall 为 77.9%**，事实忠实度 **Faithfulness 为 81.4%**。
> - 在 DEV 消融实验中，Full 检索链较 BM25-only（16.7%）和 Dense-only（37.5%）实现了稳健的净增益（Recall@5 达到 50.0%）。

**【局限性与总结】（4:00 - 5:00）**
> 客观来看，系统当前的 **Context Precision 为 41.2%**，说明 Top-5 中仍混有未引用的背景上下文，这也是后续引入动态阈值过滤的重点改进方向。
> 总结而言，FORAG 成功构建了可落地的垂直领域高质量 RAG 闭环。汇报完毕，请各位老师批评指正！

## 四、本人负责模块深度解析 (Retriever Core Deep-Dive)

### 1. BM25 与 Dense 双路召回
- **BM25 优势**：对专有名词（如 `DWR`、`eVent`、`Nikwax TX.Direct`、`GORE-TEX Pro`）和特定数字（如 `40℃`、`两次漂洗`）实现确定性精确倒排召回。
- **Dense 向量优势**：采用 `intfloat/multilingual-e5-small`（384 维），通过 `passage: ` 与 `query: ` 指令前缀，捕捉口语问题（如“衣服吸水变暗”、“表面不挂水珠”）与专业术语（“DWR 涂层失效”）之间的语义关联。

### 2. RRF 倒数排名融合算法 (Reciprocal Rank Fusion)
- **公式**：
  $$RRF\_Score(d) = \sum_{m \in \{BM25, Dense\}} \frac{1}{k + r_m(d)}$$
- **参数**：平滑常数 $k=60$。
- **为什么不直接使用分数加权（Score Blending）？**
  - BM25 分数是无上界的词频统计值（如 0~35），而 Dense 是余弦相似度或内积（如 0.6~0.9）。两者的数值分布和尺度随不同 Query 剧烈波动，人工固定权重极易在不同提问上过拟合。RRF 仅依赖排名序号，具备极强的无参数鲁棒性。

### 3. Cross-Encoder 深度重排
- **模型**：`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`。
- **与 Dense（Bi-Encoder）的区别**：
  - **Dense（Bi-Encoder / E5）**：Query 与 Document 分别编码为固定向量，仅计算点积或余弦，计算高效，适合海量知识的大规模候选召回。
  - **Cross-Encoder**：将 Query 与 Document 联合输入模型，利用两者之间的细粒度 Token 交互进行相关性评分，交互更充分但计算成本更高，因此只用于 Top-30 候选重排。

## 五、答辩高频追问题库与标准应答 (30+ Questions)

### 【第一部分：基础概念类】(1-10)

#### Q1: 为什么要选择户外服装养护这个垂直场景？
**答**：户外功能服装是高客单价、强知识密度的垂直领域。洗护不当（如用错含柔顺剂的洗衣液、高温烘干）会直接导致防水透气膜分层失效。该领域官方权威资料明确，但用户口语表达与官方规范差异大，非常适合通过知识库与混合检索构建高可靠 RAG。

#### Q2: 知识库包含多少数据？来源是什么？
**答**：知识库包含来自 Arc'teryx、GORE-TEX、Patagonia、Nikwax、Grangers 等 14 个官方权威来源，共清洗切分为 234 个规范切片。

#### Q3: 为什么切片大小设定为 60~320 Token？
**答**：户外服装洗护指南多以操作步骤、注意事项和参数说明为主。60~320 Token 刚好能容纳 1~2 个完整的清洗或烘干操作步骤，既避免切片过碎丢失前后主语，又避免切片过长稀释检索向量语义。

#### Q4: E5 模型为什么要在文本前加 `passage: ` 和 `query: `？
**答**：这是 E5 系列模型的非对称检索训练规范。显式添加前缀有助于模型区分待检文档与查询请求，在跨语言和非对称检索中获得更好的相似度对齐效果。

#### Q5: Elasticsearch 9.5.1 在项目中承担什么角色？
**答**：ES 充当统一的混合搜索引擎。我们在同一个索引 `fashion_care_kb_v1` 中同时定义了 `content` 字段的 BM25 中文分词倒排索引，以及 `embedding` 字段的 384 维 HNSW 稠密向量索引。

#### Q6: Top-K 最终为什么设定为 5？
**答**：在前期实验中，Top-5 能够在保持 87.5% 召回率的同时，将上下文 Token 长度控制在生成模型的最佳注意力区间，避免 Top-10 引入过多冗余噪声。

#### Q7: 什么是 RAG 中的幻觉？FORAG 如何降低无依据生成风险？
**答**：幻觉指模型生成与客观事实不符或未经证实的内容。FORAG 通过多道防线降低无依据生成风险：① 混合检索提供精准切片；② Evidence Judge 前置过滤不充分证据；③ 提示词要求基于检索上下文回答并标注 `[E#]` 出处，在证据不足时通过保守路由安全终止。

#### Q8: 系统的三大业务状态是什么？
**答**：`answered`（证据充分并生成回答）、`needs_more_information`（缺少关键信息引导补充）、`insufficient_evidence`（超出知识库范围安全终止）。

#### Q9: 为什么系统设计为单轮无记忆？
**答**：功能服装洗护多为针对特定衣物的独立咨询。无状态单轮架构能避免上一轮会话的历史上下文干扰当前检索，保证单次检索与生成的独立性与可复现性。

#### Q10: Sources 与 Evidence 的区别是什么？
**答**：Sources 指回答中实际引用标注 `[E#]` 的官方资料出处链接；Evidence 则指检索系统筛选出的 Top-5 核心候选切片。在信息不足或证据不足时，候选切片仅供参考，不作为最终回答依据。

### 【第二部分：核心技术与算法类】(11-20，重点针对本人负责模块)

#### Q11: 为什么需要 BM25 和 Dense 双路召回？
**答**：因为两路存在显著互补。BM25 擅长精准命中专有名词（如“GORE-TEX Pro”、“DWR”）、品牌与固定参数；Dense 向量擅长捕捉口语化表达（如“表面吸水变暗”、“透气不行了”）的语义关联。消融实验证实两者存在各自独占命中的样本。

#### Q12: 为什么 RRF 在 Top-5 口径下没有产生净 Recall 提升还要保留？
**答**：RRF 的核心价值在于「**融合异构排名并避免直接比较原始分数**」和「**候选池质量保障**」。BM25 得分与 Dense 向量余弦值位于不同评分空间，无法直接线性相加。RRF 根据各路 candidate 的排名位置进行融合，去重并合成高质量的 Top-30 候选池。虽然受限于 Top-5 截断，RRF 在 Top-5 上未直接提分，但它为后续 Cross-Encoder 重排提供了统一优质的候选空间，最终通过 CE 实现了 +3 hits 的净提升。

#### Q13: 为什么不对知识库全量 234 条切片直接用 Cross-Encoder 打分？
**答**：Cross-Encoder 计算复杂度高（需对 Query 和 Document 联合输入并进行细粒度 Token 交互计算）。在 234 条切片上全量推理会造成明显的延迟瓶颈。业界标准方案正是「双塔快速初筛召回 + Cross-Encoder 小范围精排」。

#### Q14: Cross-Encoder 在 DEV 实验中为什么既有救回（7条）也有丢弃（4条）？
**答**：重排模型依据 Query 与切片的全局交叉交互打分。救回 7 条说明模型成功识别了深层语义相关度；丢弃 4 条说明部分切片虽然含有关键词，但在深层语义交互下得分低于其它候选切片。最终净增 +3 条（Recall 由 37.5% 升至 50.0%），体现了重排算法的正向净收益。

#### Q15: RRF 公式中的常数 $k=60$ 是如何确定的？
**答**：$k=60$ 是信息检索顶级会议 Cormack 等人提出的经典黄金常数。它能有效平衡排名靠前切片的权重衰减斜率，防止排第一名的切片权重过大导致低容错率。

#### Q16: LangGraph 状态机在系统中具体如何流转？
**答**：用户输入先进入 `Query Analysis`；若信息不足则直接路由至 `needs_more_information`；若信息完备则触发 `Hybrid Retrieval`；随后进入 `Evidence Judge`，充分则进入 `Answer Generation`，不足则判断是否触发 `Query Rewrite` 进行第 2 轮增量检索，仍不足则安全终止至 `insufficient_evidence`。

#### Q17: 最大重写次数为什么限制为 1 次？
**答**：限制 1 次是为了防止系统陷入死循环重试，同时将端到端延迟控制在可接受范围。若第 2 轮检索仍未找到证据，说明知识库确实缺乏相关内容，应果断安全终止。

#### Q18: 行内引用 `[E#]` 是如何实现的？
**答**：生成模型被严格要求在输出断言后附加 `[E#]` 标牌。系统在输出后置处理中通过正则表达式提取所有标牌，校验其编号是否在输入切片范围内，并据此构建最终的 Sources 出处清单。

#### Q19: FastAPI 后端如何保障跨域与高可用？
**答**：通过 `CORSMiddleware` 配置精确的 Origin 白名单（`localhost:5173` 与 `127.0.0.1:5173`），并通过全局异常处理器捕获引擎异常，向前端统一返回结构化的安全错误信息，不泄露内部调用栈。

#### Q20: 前端如何防止用户重复点击提交导致并发冲突？
**答**：前端设计了 `createRequestGate` 防重门禁，在请求发起时置位 `busy` 锁，同时在 UI 上将输入框和发送按钮设为 `disabled`，直至响应返回或超时才释放锁。

### 【第三部分：实验评测、失败分析与局限性】(21-30+)

#### Q21: 为什么 DEV 上 Full 检索只有 50.0%，而正式 TEST 上达到了 87.5%？能否直接对比？
**答**：**不能简单纵向当作同一个实验对比。**
原因有三：① 评测口径不同：DEV 消融是针对 Standalone 检索器（直接输入原始 Query），而 TEST 是经过 LangGraph 意图解析规范化后的端到端全链路检索；② 样本集不同：DEV 包含 24 条可评测样本，TEST 包含 16 条正式盲测样本；③ 集成阶段不同：全链路中的 Query Analysis 帮助消解了部分歧义。两者分别反映了模块级消融与系统级最终表现。

#### Q22: Context Precision 只有 41.2%，这代表什么？为什么会偏低？
**答**：Context Precision 衡量的是检索出的 Top-5 切片中与回答实际所需事实的纯度。41.2% 说明在 5 条候选切片中，约有 2~3 条切片包含未被直接引用的背景信息或弱相关描述。这是系统的**主要性能限制**，主要由于固定 Top-5 窗口以及段落级切片包含多句背景文字所致。

#### Q23: Claim Recall (77.9%) 和 Recall@5 (87.5%) 为什么不一致？
**答**：Recall@5 是切片级召回率（只要命中了包含答案的切片即算成功）；而 Claim Recall 是 RAGChecker 细粒度的事实级覆盖率（统计生成回答覆盖了黄金答案中的多少条原子事实声明）。在复合条件（如同时涉及水温、专用洗剂、漂洗次数与低温烘干）问题中，即使召回了切片，回答也可能遗漏次要细节，导致 Claim Recall 略低于切片召回率。

#### Q24: DEV 消融中未命中的 12 条样本，具体失败原因是什么？
**答**：经过逐条归因分析：
- **5 条为前置召回损失**（正确证据在前置 BM25 和 Dense 中均未进入 Top-20，属于词汇不匹配或语义跨度过大）；
- **0 条为融合排序损失**（召回命中的证据均成功保留在 RRF Top-30 中）；
- **7 条为重排损失**（正确证据在 Top-30 中，但 Cross-Encoder 打分未能排进 Top-5）。

#### Q25: 系统的端到端耗时是多少？主要瓶颈在哪里？
**答**：在本机测试环境下（i7-8750H, 16GB），3 个测试样本的端到端均值约为 9.7 秒。耗时瓶颈主要在远端大模型 API 调用（Query Analysis 约 2.9 秒，Evidence Judge 约 1.5 秒，Answer Generation 约 5.4 秒）；本地检索（BM25+Dense+RRF+CE）耗时稳定在 1.7 秒左右。

#### Q26: 为什么不把 terminal 终止样本的耗时计入 Answer Generation 均值？
**答**：因为当系统判定为 `needs_more_information` 或 `insufficient_evidence` 时，根本没有触发大语言模型生成，而是通过确定性字典映射直接输出（耗时 < 1ms）。若将其计入生成均值，会虚假拉低大模型实际生成的延迟统计。

#### Q27: 如果知识库增加到 10 万条切片，当前架构需要做哪些改造？
**答**：① 向量检索端：当前 ES HNSW 仍可承载，但可考虑分布式分片与量化索引（PQ/SQ）；② 重排端：维持双路召回 Top-20 与 RRF Top-30 不变，Cross-Encoder 仅需对 30 条切片打分，重排计算量不随知识库总规模线性增长；③ 知识库维护：引入增量切片与版本隔离机制。

#### Q28: 为什么不直接使用开源的 LangChain 或 LlamaIndex，而是使用 LangGraph？
**答**：户外服装养护需要严格的状态流转控制（如证据不足重写、条件分支拒绝）。传统的线性链式调用难以优雅表达循环、条件分支与显式状态机，而 LangGraph 提供了基于图的强类型状态流转控制，具备确定性与可观测性。

#### Q29: 项目在工程测试方面做了哪些工作？
**答**：构建了全栈回归测试体系：后端使用 Pytest 编写了 146 个单元与集成测试（涵盖索引、检索、状态机与 API）；前端编写了 8 个基于 Node.js 原生测试框架的单元测试，并使用 Playwright 完成了 67 项跨分辨率与多业务状态的端到端回归。

#### Q30: 针对当前系统限制，下一步最优先的优化是什么？
**答**：最优先优化是**动态重排阈值与细粒度切片过滤**。通过设定 Cross-Encoder 得分截断门槛，只向大模型输入真正高置信度的 1~3 条切片，直接解决 Context Precision 偏低的问题，并减少生成阶段的 Token 消耗与延迟。
